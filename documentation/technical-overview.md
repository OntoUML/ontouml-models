# Technical overview

[Documentation index](README.md) · [Using models](using-models.md) · [Contributing](contributing.md) · [Script guides](../scripts/README.md)

This guide explains the repository's files, generated artifacts, and validation boundaries. For downloads and a concrete example, start with [Using models](using-models.md).

## Models, distributions, and metadata

A **model** describes concepts and relationships in a domain. A **distribution** is a file representing that model, such as a native project, JSON export, RDF graph, or diagram. **Metadata** describes the model or a distribution: its title, contributors, sources, format, identifiers, and other catalog information. The term **dataset** in the scripts and RDF metadata refers to a cataloged model, not necessarily a collection of instance records.

### Inputs and generated outputs

Model-specific paths below are relative to `models/<slug>/`, where `<slug>` is the model folder name.

| File or directory | Role and source of truth |
| --- | --- |
| `ontology.vpp` | Contributor-maintained Visual Paradigm project, original or reconstructed. The repository does not export JSON from it. |
| `ontology.json` | Contributor-maintained JSON export; canonical input for the model's RDF graph. Keep it consistent with the native project. |
| `ontology.ttl` | Generated, committed model RDF in Turtle syntax, produced from `ontology.json` using the language declaration in `metadata.yaml`. Do not edit it manually. |
| `metadata.yaml` | Author-maintained descriptive model metadata. The submission helper can normalize this source file. |
| `references.bib` | Optional contributor-supplied bibliography. It is structurally validated when present; it is not generated by the submission helper. |
| `original-diagrams/` | PNGs representing the authors' original diagrams, including images obtained from source publications. |
| `new-diagrams/` | PNGs of diagrams recreated in Visual Paradigm. Neither PNG directory is generated from VPP by this workflow. |
| `metadata-json.ttl`, `metadata-vpp.ttl`, `metadata-turtle.ttl` | Generated distribution metadata for the corresponding model file. Inputs include source metadata, the distribution file, and retained existing RDF values. These files describe files; they do not contain the model itself. |
| `metadata-png-o-<name>.ttl`, `metadata-png-n-<name>.ttl` | Generated metadata for each direct PNG in the original or recreated diagram directory. `<name>` is the image filename without `.png`. |
| `metadata.ttl` | Generated model-level RDF metadata from `metadata.yaml`, retained catalog-managed values, and distribution identifiers discovered from the sidecars. This is not `metadata-turtle.ttl`. |
| Root `catalog.yaml` | Author-maintained, non-derived catalog-level metadata. |
| Root `catalog.ttl` | Generated catalog metadata combining `catalog.yaml`, model dataset membership and contributors from model-level `metadata.ttl`, and the previous catalog's semantic state and dates. |
| Release `ontouml-models-YYYYMMDD.ttl` | Aggregated RDF from eligible repository Turtle files. It does not bundle VPP, JSON, PNG, YAML, or bibliography files. See the [aggregation contract](../scripts/generate-release-file.md#local-aggregation-contract). |

A normal submission needs at least one valid PNG directly inside either accepted diagram directory; both directories are not required. Individual historical folders can contain additional files. The [submission guide](../scripts/process-new-model-submission.md#required-source-files) defines the current input requirements.

Metadata generation is **not a stateless YAML-only conversion**. Existing RDF can supply stable model/distribution identities, curated values, links, and metadata timestamps. Deleting a generated file and recreating it is therefore not necessarily equivalent to regenerating it in place. The [model metadata guide](../scripts/metadata_yaml_to_ttl.md#existing-metadatattl-preservation) and distribution guides specify what is retained.

## Conversion and independent versions

Export from Visual Paradigm to JSON is a contributor/tool step, commonly using the [OntoUML Plugin for Visual Paradigm](https://purl.org/ontouml-vp). Repository automation starts from the supplied JSON; it does not establish native-project/JSON equivalence.

The repository wrapper pins `ontouml-json2graph==2.0.1`. If `metadata.yaml` declares one distinct language, generated `ontouml:name` literals use that language tag. With several distinct languages, names are untagged; the wrapper does not infer a language for each name. See the [conversion contract and examples](../scripts/generate-ontology-turtle.md#transformation-contract).

Conversion can succeed with warnings: invalid cardinalities and stereotypes are preserved under the selected policies, unresolved diagram target links are omitted, path-point order is not represented, and property-assignment maps are omitted. Consult the [exact warning policies](../scripts/generate-ontology-turtle.md#explicit-warning-policies) before assuming RDF is a lossless substitute for JSON. A stored `ocmv:isComplete` value is not proof of lossless conversion or native-project equivalence.

| Versioned component | Meaning |
| --- | --- |
| Repository commit or date tag | A snapshot of repository files; release tags use `YYYYMMDD`. A date is not a converter version. |
| JSON2Graph converter | The exact software dependency in [requirements](../scripts/requirements.txt), also enforced by the [wrapper](../scripts/generate_ontology_turtle.py). |
| [OntoUML Metamodel](https://w3id.org/ontouml/metamodel) | Implementation-independent concepts used to describe OntoUML models. |
| [OntoUML Schema](https://w3id.org/ontouml/schema) | JSON representation specification, maintained separately from this catalog. |
| [OntoUML Vocabulary](https://w3id.org/ontouml/vocabulary) | RDF terms for model content, distinct from catalog metadata terms. |
| [Catalog Metadata Vocabulary](https://w3id.org/ontouml-models/vocabulary) and reused metadata vocabularies | Terms for describing the catalog, models, and distributions. Their versions do not follow repository date tags. |
| Stored [SHACL shapes](../shapes/) | RDF metadata constraints versioned with this repository; their presence does not mean CI executes them. |

Do not infer a shared version from these links or the repository release name. For reproducible processing, retain the repository commit and converter version; record the schema/vocabulary versions actually used by your own tools. Local environment and platform guidance is maintained in the [script index](../scripts/README.md#local-setup).

## Identifiers and URLs

An RDF **IRI** identifies a resource. A file download URL or repository folder URL serves a different purpose, even when both look like web addresses.

| Identifier or URL | What it identifies or provides |
| --- | --- |
| Dataset IRI in `metadata.ttl` | The cataloged model as a dataset. Existing identities are retained; new model metadata uses a deterministic UUIDv5 identity based on the folder name. |
| Distribution IRI in a `metadata-*.ttl` sidecar | A particular file distribution. Existing identities and curated fields can be retained; see the corresponding generator guide. |
| `https://w3id.org/ontouml-models/model/<slug>#<element-id>` | A model-content resource in generated `ontology.ttl`. The project IRI ends with the exact top-level JSON project ID. These are not the metadata's UUID-based dataset/distribution IRIs. |
| `dcat:downloadURL` | A file download location, normally a raw GitHub URL; a branch-based URL can change over time. |
| `ocmv:storageUrl` | The repository storage location for a dataset or catalog. |
| [Persistent catalog URLs](../README.md#catalogs-persistent-urls) | Stable entry points intended to redirect to repository, release, vocabulary, shape, or discovery resources. A persistent entry point is not automatically a fixed content snapshot. |

Preserve exact RDF identifiers. For example, the [ROT metadata at the inspected commit](https://github.com/OntoUML/ontouml-models/blob/324d71e82d4430fff5e2b84e38ca9620a94c5987/models/amaral2019rot/metadata.ttl) types the dataset IRI ending in `d88fe48c-d574-43b4-85d6-a6e1aeaa6726/`, but places distribution links on an IRI without that final slash. These are distinct RDF IRIs, not interchangeable spellings. Successful synchronization can preserve such legacy inconsistencies; it does not repair or certify every relationship. Do not normalize slash/hash forms when reproducing an analysis.

## What validation establishes

| Check | What it establishes | What it does not establish |
| --- | --- | --- |
| YAML validator | Supported fields, syntax, types, required values, controlled values, and configured warnings | Complete submission readiness, legal rights, or SHACL conformance |
| JSON preflight and ontology wrapper | UTF-8 JSON object, project ID, usable language, successful conversion, generated namespace/project/name-language rules | Full JSON Schema conformance, native VPP equivalence, or model semantic quality |
| VPP and PNG checks | VPP file presence/non-emptiness and filename shape; PNG signature/IHDR structure | Native project validity, correct diagram content, or full image decoding |
| Bibliography validator | Basic BibTeX/BibLaTeX structure when `references.bib` is present | Required bibliographic fields for every entry type or factual correctness of citations |
| Turtle parsing | Syntactically parseable RDF for the files checked | SHACL conformance or correct domain modeling |
| Generation/synchronization checks | Agreement with the selected generators and their comparison rules | Exhaustive semantic review, rights confirmation, or live discovery-service synchronization |

The current submission workflow does not run JSON Schema or SHACL validation engines. Warnings can be nonfatal. Read the [submission validation boundary](../scripts/process-new-model-submission.md#what-the-helper-checks-before-generation), inspect warnings, and review the actual final PR head. A green unrelated check, or no check triggered by a documentation-only change, is not evidence that all these checks ran.

### Change detection and timestamps

| Artifact | Comparison and timestamp consequences |
| --- | --- |
| `ontology.ttl` | Normal generation uses RDF graph isomorphism: equivalent graphs preserve the existing file byte-for-byte. Migration-only force materialization uses a different rule; see the [generator guide](../scripts/generate-ontology-turtle.md#source-of-truth-and-output-policy). |
| Model and distribution metadata | Serialized content is compared. Even formatting-only differences can cause a rewrite and update `fdpo:metadataModified`; existing `fdpo:metadataIssued` is preserved. Required new dates come from the explicit metadata timestamp. |
| Root `catalog.ttl` | RDF semantics determine dates. Membership changes update both `dct:modified` and `fdpo:metadataModified`; metadata-only changes update the latter. A formatting-only rewrite does not advance either date. |

Changing ontology content alone need not change the Turtle distribution's metadata timestamp when its metadata stays the same. Model `issued`/`modified` values and generated metadata timestamps describe different things. Use the [model metadata preservation rules](../scripts/metadata_yaml_to_ttl.md#existing-metadatattl-preservation), [distribution guides](../scripts/README.md), and [catalog timestamp rules](../scripts/generate-catalog-file.md#modification-timestamps) for exact behavior.

This existing image is a conceptual overview, **not the current normative validation specification**. In text: a catalog links to model datasets; a model links to its distributions; a distribution records its format and download location. Shared resource metadata supplies descriptions, dates, licenses, and people/organizations. Model metadata also records language, theme, purpose, context, representation style, and sources.

Known differences between the image and the stored shapes are:

| Property | Image | Stored shape |

Stored shapes are not currently executed by the submission workflow.

## GitHub storage and FDP discovery

GitHub stores and distributes the files, records their history, accepts contributions, and runs the documented repository automation. The [FAIR Data Point](https://w3id.org/ontouml-models) is a separately operated discovery layer for catalog metadata. Repository-side `catalog.ttl` synchronization is not evidence that a live FDP has indexed or synchronized that content. FDP endpoints, search, deployment, and operational behavior are outside this guide's inspected scope; useful [FDP references](../README.md#fair-data-point-the-data-discovery-service) remain available.
